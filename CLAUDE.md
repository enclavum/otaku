# CLAUDE.md

Notes for AI assistants working on otaku. This file is generated by the
assistant. The ultimate, manually written source of truth is
`docs/product_design.md` — every change must be checked against it; when
this file and the product design disagree, the product design wins. It
says itself that it is partly outdated: the code is what otaku does now,
the product design what it means to do. The code's structure has a home
of its own, `docs/code_structure.md`, and the rules of each area one in
`.claude/rules/` ("Rules by area", below).

## What otaku is

An LLM frontend for creative writing and roleplay, talking to
OpenAI-compatible servers (Ollama, omlx, KoboldCpp, and others). Chats
are stories that can be branched from any message. A background pass
extracts lore from played messages — scenes, characters, journals — and
the context sent to the model keeps the opening and the recent tail
verbatim with scene summaries in between. Database encryption is opt-in
— plain text is the default.

## Environment and commands

Python 3.11 in the `otaku` conda environment:

    conda activate otaku && otaku       # run the app — see below
    make lint RUN="conda run -n otaku"  # ruff check (Makefile defaults to uv)
    make format RUN=...                  # ruff format
    make typecheck RUN=...               # mypy (strict)
    make test RUN=...                    # pytest over tests/, the unit suite
    make scenarios RUN=...               # pytest over scenarios/ — .claude/rules/tests.md
    make regression RUN=...              # the slow screen scenarios alone
    make test-model                      # a fake llama.cpp on :8080 — scripts/test_model.py

The app must NOT be launched through a bare `conda run`: it pipes stdin
and stdout, and a terminal that cannot be reached answers nothing — no
cursor position (the screen-erasing paths give up) and no background (every
adaptive color falls back). `conda activate` first, or pass
`--no-capture-output`. Lint, typecheck and the test suites are unaffected;
only what talks to the terminal is.

The state dir defaults to `~/.otaku`, relocatable via the
`OTAKU_CONFIG_DIR` env var.

## Architecture

The code's layout is `docs/code_structure.md`: the layers and what each
may import, the backend's interface over its domain, the mirror of `app`
and `story` twins in five places, the machinery, each frontend's door,
the terminal's, the web's and the page's layouts, how the two frontends'
parts correspond, and a call followed from either frontend down to the
store. Read it before moving code or adding a module.
`tests/test_architecture.py` reads the tree and holds what a scan of it
can check, so an import that crosses a layer fails the suite rather than
the review; `docs/diagrams.md` draws the module graph and the control
flow. What follows is what the layout does not say and every session
needs: who owns a rule, the story a client holds, the interface as a
client uses it, and names.

### Who owns a rule

The `web` row of the layer table (`docs/code_structure.md`) is the
standing test for what belongs in `backend` (anything both frontends
would need) versus a frontend (only the medium).

A DECISION lives below both frontends; a LOOK lives in one. Anything the
two would have to agree on — what a played line's syntax means, what a
story is called, what goes in the context window — belongs to
`backend`, `context` or `settings`. Anything that is the medium — a key
binding, a column width, a menu's order, what a screen is made of —
belongs to the frontend, and the other must not inherit it. A rule one
frontend copies from the other names its twin's home in a comment
(`docs/code_structure.md`, "The two frontends"); the language barrier is
the one reason a rule may exist twice.

What must MATCH between the two is what a thing means, never how it
looks — a played turn is a band the reader can pick out, dialogue takes
one accent, a derived field refuses to be edited — and the drawing is
each medium's own: change what one of those means and change it in
both; change how it looks and change nothing else.

A report is a resource read with `get` (`api.usage`, `api.info`,
`api.balance`, a story's `api.stories.context` and its `fill`) answering
the FACTS and `text()`: a page draws the facts, a terminal prints the
text, the two need not carry the same rows, and a frontend that parses
the text back into fields has taken the wrong half.

A frontend reads ONE settings slice, its own, through the interface —
`api.settings.terminal.get()`, `api.settings.web.get()` — never the
file; anything a story depends on — a window, a template, a provider —
is read below both.

What a typed argument MEANS is the terminal's door's (`terminal.api`),
since typing a command is its medium and the page reaches every one by a
button; what a model's own settings take is the backend's, for both
(`backend.domain.app.models`), the page's fields passed through as typed.

### The story a client holds

The app holds no story (`docs/code_structure.md`, "The interface"); each
frontend holds its own — the terminal's `Chat`, the page's
`js/play/held.js`, so two tabs may play two stories — and names the head
it last saw on every write that moves it (`expected_head`; over HTTP
`If-Match`). A story is made by the first write that lands and taken
back where that write is refused or abandoned (`Chat.writing`,
`held.writing`), so none is left behind empty. The story a launch
RESUMES is one pointer for both, `last_story`, written by every landing
in either frontend. A story not made yet has no `Story.can_attach`: both
frontends read the model in use's `capabilities.vision` instead
(`Chat.can_attach`, the page's `factsOf`) — change one, change both.

### The interface, as a client uses it

How the backend is reached — one door per frontend, the interface's
resource classes and their verbs, its entities and `Changed`, the domain
below it and the machinery beside both — is `docs/code_structure.md`'s
("The interface", "The domain", "Machinery", "A frontend's api
package"). A representation carries everything a client needs to show
it, so a client CALLS THE RESOURCES AND NOTHING ELSE — no helper, rule or
vocabulary of the backend's beside them, the story's language
(`backend.api.story.language`) the one exception — and what a client
finds missing is a representation's field to add, never a function to
export. A check before a write is the write asked to validate only
(`api.stories.cards.create(…, validate_only=True)`; over HTTP
`?validate_only=true`).

A frontend touches the `App` for its life and its channels alone
(`start_worker`, `note_typing`, `note_submission`, `record_crash`,
`set_on_idle`) and asks everything else through the facade.

### Names

A BOOLEAN property is never named by a noun or a verb. One that says
whether the object IS something is `is_…`; one that says whether it CAN
do something is `can_…` (`can_manage`, `can_count_tokens`,
`can_mark_cache`); an adjective or a participle stands on its own
(`fresh`, `quiet`). So `manages_models` and `counts_tokens` are not
booleans' names. The one exception is a CAPABILITY
(`ModelCapabilities.vision`, `text_completion`): those are the trade's
own words, spelled as every engine spells them. Applied in
`otaku/providers` so far; a new boolean anywhere follows it.

A request's size is told by five numbers, each with ONE name everywhere
the backend speaks — its code, `backend.api`, the HTTP surface and its
spec: `context_length` (the model's own maximum), `context_loaded` (what
the running instance serves), `context_window` (what a request gets on
the model), `context_limit` (the reader's cap, 0 for none — the one
exception: the config key and `/set max_context` keep `max_context`) and
`context_in_force` (what a request is cut to, `assembler.context_in_force`
the one rule).

## Rules by area

The rules one area alone needs are in `.claude/rules/`, a file per area,
loaded into a session once it reads or edits a file the rule file's
`paths` name. Work that decides something in an area before opening any
of its files reads that file first:

- `story.md` — a story's settings and its layout, the two facts derived
  from the layout (the look and the wire), the canvas and the join rule,
  the page's tail, the text wire, the context fill.
- `tools.md` — what a tool call is, the tools and their names, the play's
  events, how each frontend draws a call; injections.
- `language.md` — the story's language, what a played line reads as in
  both frontends, the terminal's commands, the `@` sigil.
- `web.md` — the one thread, what the server and the page must agree on,
  `api.yaml`, the demos.
- `integrations.md` — the integrations and the web search key, a
  server's locality, pictures on the wire.
- `config.md` — the configuration files and how otaku writes them, the
  model in use and the extraction pin, the three migration frameworks.
- `data.md` — the data model, a message's pictures, the store's
  conventions.
- `tests.md` — what a test may assert, the two suites, the markers.

A rule belongs in this file when every session needs it, and in an
area's file when only work on certain files does — its `paths` naming
them all, across packages where the rule spans them.

## Documentation rules

1. Docs describe the final state only — never history or comparisons — and
   each doc has one owner topic: the product's intent is
   `docs/product_design.md`'s, the code's structure
   `docs/code_structure.md`'s, the rules neither holds this file's and
   `.claude/rules/`'s.
2. A change updates its relevant doc in the same commit as the code.
3. The code documents itself first: module docstrings say what a module owns;
   comments only for non-obvious whys. Docs cover what code can't: product
   intent, cross-module contracts, operational rules.

## Copy conventions

SENTENCES COME FROM THE BACKEND, verbatim. A frontend never rewords a
refusal, a notice or a report — it decides only WHERE the text appears.
Wording about the medium itself ("close · esc", "Press CTRL+C to quit",
a key caption, a fault the reader can do nothing about) is the
frontend's alone. Where a sentence cannot be asked for (the page has no
story, so no endpoint to ask), it is COPIED with a comment naming its
home.

User-facing printed messages start with a capital letter, but for a
sentence that opens with the product's name, which keeps it lowercase
("otaku is down"). Deliberately lowercase too: the `otaku: …` stderr
warnings (the Unix `program: message` convention), system-log lines,
the transient status-line fragments a worker updates in place, and the
dim `[ … ]` report blocks beside a turn (the stats line's family).

## Module conventions

Dependencies stay minimal; no optional extras.

Order within a module: constants, then classes, then functions — public
before protected. Logical grouping wins over the order: a private helper
that belongs to a public function stays beside it, and a section comment
names each group when a module has several. Two layouts are fixed by
their layer: an interface module holds its resource classes, then their
builders, then the entities they answer (`docs/code_structure.md`, "The
interface"), and a `web.api` module ends with its rows (`ROUTES`,
`STREAMS`).

A name is protected (`_leading_underscore`) when nothing outside its
module uses it — constants included — so a reader knows what they may
use and a rename stays local; a hook for subclasses is declared on its
base, so the extension surface is visible in one place. The protected
module and the protected member are `docs/code_structure.md`'s
("Protected names").
